# Unbazarbot — Project Instructions

Проект: `dilukhin/unbazarbot`.

Цель проекта — поддерживать Telegram-бота `@unbazarbot`, который расшифровывает голосовые сообщения через RouterAI, работает в личке и группах, допускает ручное `/tr` по reply и контролируемое автоматическое распознавание в разрешённых группах.

## Источники истины

Для фактического состояния реализации первым источником является актуальный `main` GitHub: код, config, документация и история изменений.

В начале существенной задачи прочитай `github_project_bootstrap.md`, затем актуальные:
- `README.md`;
- `docs/project_baseline_ru.md`;
- `docs/current_status_ru.md`;
- `docs/architecture_ru.md`;
- `docs/security_model_ru.md`;
- `docs/work_plan_ru.md`;
- относящиеся к задаче файлы кода.

План, старый диалог, память и handoff — контекст, но не доказательство текущей реализации.

## GitHub-first

Для GitHub использовать Connector первым и как основной удалённый транспорт. Не пробовать `git` или `gh` только ради проверки доступности. Для multi-file write через Connector предпочитать Git Data flow `blob -> tree -> commit -> ref`. Перед обновлением ref проверить HEAD, после значимой записи сделать targeted read-back.

Если Connector не даёт требуемую операцию, сначала явно зафиксировать нужную operation и подтверждённый gap; только затем выбирать другой транспорт.

## Архитектурные инварианты

- Telegram transport: long polling, пока нет отдельного принятого решения о webhook.
- STT выполняется внешним RouterAI; VPS не должен становиться тяжёлым локальным ASR-хостом без отдельного решения.
- Доступ группы по умолчанию запрещён.
- Группа получает право использования только через approval администратора бота: одноразовый либо постоянный.
- Админские аккаунты задаются Telegram `user_id`.
- `/tr` как reply — поддерживаемый способ расшифровывать старые сообщения, доступные в Telegram reply context.
- `/auto_on` относится ко всему Telegram `chat_id`; forum topics отдельно пока не моделируются.
- Несколько STT-моделей задаются alias-ами в config и могут переключаться без переписывания Telegram-логики.
- Кеш привязывается как минимум к `file_unique_id + model_alias`.
- Секреты не входят в Git.

## Безопасность и приватность

Никогда не публиковать Telegram bot token, RouterAI API key, содержимое `.env`, runtime SQLite DB, приватные расшифровки или аудиофайлы.

Любая новая возможность, способная увеличить расход RouterAI (например, публичное использование в личке, глобальный auto-mode, обработка новых типов файлов), должна сохранять явную модель доступа и лимитов.

Изменения production VPS, BotFather, RouterAI account, systemd и реальных group approvals выполнять только по явному поручению пользователя. Сначала описывать target и expected state, после изменения проверять результат.

## Документация

Устойчивые решения — в baseline/architecture/security docs. Текущее состояние, незакрытые расхождения и runtime evidence — в `docs/current_status_ru.md`. Следующие работы — в `docs/work_plan_ru.md`.

Не описывать как реализованное то, чего нет в текущем `main`. Если пользовательский runtime опережает GitHub, явно назвать расхождение и предложить синхронизацию.

Общение и проектная документация — по-русски; код и технические идентификаторы — преимущественно по-английски.

### Переход в новый диалог

Если текущий диалог становится настолько перегруженным, что объём контекста может снизить точность дальнейшей работы, ChatGPT должен самостоятельно предложить перейти в новый диалог.

Перед переходом необходимо:

* подготовить краткий стартовый промпт с текущей задачей, достигнутым состоянием, важными решениями, ограничениями и следующими действиями;
* при большом объёме контекста подготовить отдельный handoff-документ с подробностями, которые нецелесообразно включать в стартовый промпт;
* указать, какие актуальные документы, исходники, отчёты или другие материалы следует приложить к новому диалогу;
* не переносить устаревшие, промежуточные и несущественные сведения.

Переход в новый диалог не должен менять принятые требования, решения и текущее состояние проекта.

### Серия действий и продолжение выполнения
Если начата серия явно определённых действий (например, последовательность операций через инструменты), после успешного выполнения промежуточного шага не переходить обратно в режим анализа или обсуждения. Выполнять следующий однозначно определённый шаг до достижения конечного состояния или появления реальной блокировки.
### Execution continuity rule:
После начала подтверждённой серии действий сохраняй выбранный execution path. Не заменяй выполнение следующего однозначного действия объяснением, планированием или повторным review. Останавливайся только при:
- ошибке инструмента;
- изменении исходных условий;
- отсутствии необходимых данных;
- явном требовании пользователя остановиться.
