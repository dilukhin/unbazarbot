# Unbazarbot — Project Baseline

Статус: persistent project baseline  
Дата актуализации: 2026-09-18  
Канонический репозиторий: `https://github.com/dilukhin/unbazarbot`

Документ фиксирует устойчивые границы проекта. Он не должен содержать текущий SHA, активный процесс на VPS, баланс RouterAI или временный статус конкретной группы.

## 1. Цель

Unbazarbot — Telegram-бот для преобразования голосовых сообщений и аудио в читаемый текст с контролируемым доступом и предсказуемой стоимостью внешнего распознавания.

Основные пользовательские сценарии:
- ручная расшифровка сообщения командой `/tr` в reply;
- автоматическая расшифровка новых аудиосообщений в явно разрешённой группе;
- расшифровка в личке в соответствии с access policy;
- выбор одной из нескольких STT-моделей через конфигурацию.

## 2. Scope

Проект отвечает за:
- Telegram Bot API integration;
- RouterAI STT integration;
- group approvals и admin workflow;
- конфигурацию моделей;
- лимиты и валидацию медиа;
- кеширование результатов;
- SQLite runtime state;
- эксплуатацию как лёгкого Linux service.

За пределами базового scope:
- чтение произвольной старой истории Telegram через user-account/MTProto;
- тяжёлое локальное ASR на VPS;
- web-панель администрирования;
- хранение архива исходных аудиофайлов;
- обработка forum topics как отдельных policy scopes, пока это отдельно не принято.

## 3. Source of truth

Для фактической реализации:
```text

2. stable normative docs
3. current_status/work_plan
4. conversations, handoffs, memory
```

Для runtime-состояния VPS и Telegram:
```text

2. current_status

```

README или план сами по себе не доказывают наличие функции.

## 4. Архитектурные инварианты

1. VPS выполняет orchestration, а не тяжёлое распознавание.
2. STT provider отделён от Telegram handlers.
3. Доступ к платному распознаванию проверяется до отправки аудио провайдеру.
4. Группа по умолчанию запрещена.
5. Approval имеет два базовых режима: one-time и persistent.
6. Bot admins определяются устойчивыми Telegram user IDs.
7. Список STT-моделей конфигурируемый и адресуется alias-ами.
8. Повторная обработка одного Telegram-файла той же моделью по возможности использует кеш.
9. Секреты и runtime user data не входят в Git.
10. Long polling остаётся default transport до явного решения о webhook.

## 5. Access model

Сущности:
- bot admin;
- Telegram group/supergroup;
- access request;
- approval decision;
- transcription job.

Постоянно разрешённая группа может использовать ручной `/tr`; auto-mode включается отдельно. Одноразовое разрешение даёт ограниченное число jobs и не эквивалентно постоянному автоматическому доступу.

## 6. Старые сообщения

Bot API не используется как механизм обхода истории группы. Поддерживаемый путь старого сообщения — пользователь делает reply на доступное voice/audio и отправляет `/tr`; Telegram передаёт контекст reply текущему боту.

## 7. Данные

SQLite является runtime store, а не repository artifact. Допустимо хранить там approvals, chat/user identifiers, jobs, cost metadata и кеш расшифровок. Исходное аудио должно быть временным, если отдельно не принято решение об архивировании.

## 8. Критерии качества

Изменение считается приемлемым, когда:
- не ослабляет access model неявно;
- не раскрывает secrets/runtime data;
- имеет предсказуемое поведение для ручного и auto flow;
- ошибки внешних API не приводят к скрытому бесконечному retry;
- новое платное поведение имеет лимиты и наблюдаемость;
- документация различает реализованный факт и план.
