Дата: 06.11.2026. Статус: **подготовлено, запуск требует отдельного разрешения
владельца**. Передача результатов UB-BZR-CHECK-01 не является этим разрешением.
[Разбор диагностики](../reports/UB-BZR-CHECK-01_review_ru.md).

Work выполнил разработку, GitHub и репозиторные проверки. Агенту поручается
только недоступная Work проверка на реальной серверной среде через существующий
доверенный ssh_relay vserv. Не разрабатывать код, не менять GitHub и не получать
новое доверие/ключи. Сначала прочитать установленную справку ssh-relay; синтаксис
не угадывать. При недоступном канале или иной идентичности узла остановиться.

## Обязательные входные данные после разрешения

- Полный 40-символьный `TARGET_SHA`, проверенный Work через Connector после
  слияния этого задания и переданный владельцу. Основание кода до этой записи —
  main `91b3cbd7cdc8b7aaa74bb1e6dd7e010f4a1a33c7`; нельзя подставлять его вместо
  актуального main автоматически. Без конкретного TARGET_SHA не выполнять задание.
- Частный отчёт UB-BZR-CHECK-01 для существующих путей и пользователя службы.
  Не брать пути из примеров и не публиковать их в GitHub.
- Явное поручение владельца именно на check/prepare и описанные ниже артефакты.

## Допустимые изменения и запреты

После разрешения допускаются: закрытый каталог исходников/подготовки, получение
кода из единственного origin dilukhin/unbazarbot, отдельный каталог нового выпуска
и его .venv с requirements.lock, update lock штатного контроллера, искусственное
аудио и временные тестовые файлы, свежая закрытая копия SQLite и проверка её
восстановления/миграции **только на копии**. Рабочие config/env разрешено читать
внутри штатных проверок без вывода содержимого. Копии с пользовательскими данными
остаются только в закрытых серверных каталогах.

Не выполнять apply, переключение current, systemctl stop/start/restart или
daemon-reload, запуск bot.py/второго опросчика, apt/обновление ОС, замену Python
или FFmpeg, изменения рабочих config/env/SQLite, разрешений групп/пользователей,
бюджетов, тарифного кеша/его pause, BotFather или RouterAI-аккаунта. Не выполнять
платные запросы. Не копировать секреты, SQLite, аудио или расшифровки на машину
агента. Не менять права/владельца существующих рабочих файлов и не удалять
старые выпуски/копии. Изменения, которые работающий бот делает сам, не относятся
к действию задания; побайтовое неизменение живой SQLite не обещать.

## Последовательность

1. Повторить выбранные метаданные UB-BZR-CHECK-01: current/.ready, версия,
   состояние службы, число процессов cgroup, NRestarts, KillMode, внешний
   интерпретатор/пути и свободные ресурсы. Ожидается работающая 0.2.0
   `2cb0965f2193e225c03ac4c9c9c6450c591df698` и один процесс. При смене выпуска,
   пользователя, путей или неожиданном состоянии вернуть расхождение до записи.
2. Использовать Python 3.12.15 из .venv действующего выпуска; не системный 3.8.10.
   Подготовить проверенные исходники TARGET_SHA вне current, выпуска и рабочих
   файлов. Существующую чистую рабочую копию разрешено использовать только если
   её путь уже известен и origin точный; проверить корень, HEAD и отсутствие
   изменений до checkout без reset/clean/force. Если путь неизвестен, разрешено
   создать новый закрытый каталог `preparation/unbazarbot` под подтверждённым
   корнем runtime и чистую копию единственного публичного репозитория там
   (`umask 077`, без переноса секретов); существующий непустой каталог не трогать.
   Не сканировать домашний каталог или другие проекты. Получить main; если он
   отличается от TARGET_SHA, остановиться и вернуть оба SHA для проверки Work.
3. Из проверенных исходников TARGET_SHA выполнить штатный
   `scripts/update_bot.py check --repo <проверенная копия>`. Затем тем же Python
   и контроллером выполнить `prepare`, передав --repo, --revision TARGET_SHA,
   --current, --releases, --config, --env-file, --database, --backups из частного
   отчёта. Использовать текущие внешние файлы, не подменять config шаблоном.
   Новый код контроллера должен быть доступен в источнике до запуска; контроллер
   0.2.0 не использовать для обхода защиты. stdout/stderr хранить закрыто на
   сервере; в отчёт переносить только проверенные безопасные итоги. Не загружать
   рабочий .env в оболочку: тесты не должны получать реальные ключи в окружении.
4. Контроллер проверяет договор денежной схемы до выполнения кандидата, создаёт
   отдельную .venv, устанавливает requirements.lock, проверяет компиляцию и весь
   pytest на искусственных данных, запускает media_doctor (ogg/mp3/wav/flac)
   под штатными ограничениями и миграцию временной согласованной копии SQLite.
   Исходная БД открывается только для чтения через SQLite backup, без ручного
   checkpoint, миграции исходника или копирования DB/WAL/SHM произвольной смесью.
   Само наличие .ready не доказывает завершения: необходим нулевой результат
   всего prepare, включая media_doctor и trial. При ошибке не продолжать и не
   менять флаги/пределы/медиа-инструменты ради обхода; незавершённый выпуск сохранить.
5. При успешном prepare штатным `scripts/maintenance.py backup` нового выпуска
   создать отдельную свежую копию в новом 0700 подкаталоге существующих backups,
   затем штатным `trial` проверить восстановление/миграцию из этой копии, указав
   её как --database и прежние --config/--env-file. Использовать Python новой .venv.
   Вызов backup проверяет quick_check; trial создаёт ещё одну временную копию и
   мигрирует её, не переписывая сохранённый снимок. Результат trial должен содержать
   database=ok, financial_schema=1, money=true и financial=true. Проверить 0600
   снимка и закрытые каталоги. Не выводить строки БД или пользовательские счётчики.
   Это испытание свежей копии, а не окончательный backup для будущего apply.
6. Повторить метаданные службы и current: по-прежнему прежний выпуск и один
   процесс; зафиксировать состояние/NRestarts, любые изменения и свободное место.
   Не считать совпадение PID единственным доказательством. Не переключать выпуск
   даже при успехе всех проверок.

## Отчёт и условия остановки

На машине агента сохранить только обезличенные UB-BZR-PREPARE-01_report.json и
краткий отчёт. Указать TARGET_SHA, UTC-интервал, коды завершения check/prepare/
backup/trial, версии Python/FFmpeg/ffprobe/prlimit, итоги compile/pytest/media
четырёх форматов/денежной схемы, проверку .ready/REVISION, права свежей копии и
итоговую неизменность выбранного выпуска/состояния службы. Рабочие пути и полные
выводы остаются на сервере. Не прикладывать config/env/SQLite/журналы тестов
целиком, ключи, идентификаторы пользователей, расшифровки и аудио.

Если штатная проверка рабочего config/env не проходит, вернуть только категорию
ошибки; не печатать значения и не исправлять их. Положительный общий RUB-предел
для prepare не требуется: решение о включении оплаты относится к следующему
этапу. После успеха Work проверит отчёт и подготовит отдельный apply с проверкой
текущего опубликованного тарифа, окончательной копией после остановки, закрытой
новой оплатой и Telegram-приёмкой. Ни это задание, ни успешный prepare сами по
себе не разрешают apply, платные испытания или запуск 0.2.0 с новой денежной БД.
