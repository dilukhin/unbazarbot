# Обновление работающего бота

Обновление **управляемое**. Оператор выбирает точный SHA основной ветки и запускает
серверный скрипт. Сделать это можно непосредственно на vserv или с рабочего/
домашнего компьютера через доверенный `ssh_relay`. Исходные аудио, база и токены
на компьютер для обновления не переносятся. Автоматической установки новых
версий, таймера и периодического перезапуска нет.

## Однократная подготовка существующей службы

Текущий бот уже работает на vserv; переносить его заново не нужно. Перед первым
обновлением агент подтверждает фактические каталоги, пользователя службы, пути
и ревизию. Пример ниже показывает схему, **не подтверждает эти пути на vserv**:

| Назначение | Пример |
|---|---|
| Рабочая копия Git для подготовки | `/opt/unbazarbot/source` |
| Отдельные выпуски и их окружения | `/opt/unbazarbot/releases/<полный-SHA>` |
| Ссылка на выбранный выпуск | `/opt/unbazarbot/current` |
| Рабочая конфигурация | `/etc/unbazarbot/config.yaml` |
| Секреты и абсолютные рабочие пути | `/etc/unbazarbot/bot.env` |
| Рабочая база | `/var/lib/unbazarbot/bot.sqlite3` |
| Закрытые резервные копии | `/var/lib/unbazarbot/backups` |

Используйте существующего пользователя службы. Он должен владеть рабочей базой,
каталогом выпусков и копий, читать рабочие настройки. Скрипт запускается от него;
не запускайте его от root поверх базы другого владельца. Файлы конфигурации,
секретов и базы имеют 0600, каталоги данных/выпусков/копий — 0700.
Пути секретов и данных должны находиться вне Git и выпусков.

Сначала создайте `current` как ссылку на **нынешний каталог работающего бота**,
сохранив его для отката. Рабочая копия Git остаётся источником подготовки и не
переключается скриптом; локальные рабочие изменения не стираются. Для `origin`
разрешён только `dilukhin/unbazarbot`. Подготовка берёт дерево точного удалённого
`main`, а не локальные незафиксированные файлы.

В сохранённой службе задайте `WorkingDirectory=<current>`,
`ExecStart=<current>/.venv/bin/python <current>/bot.py` и единственный
`EnvironmentFile=<внешний bot.env>`. Сохраните существующего пользователя и
существенные настройки службы. В `bot.env` задайте абсолютные `CONFIG_PATH` и
`DB_PATH`. Содержимое токенов не меняйте и не выводите. Применение нового файла
службы выполняет агент отдельно с принятыми разрешениями; скрипт не переписывает
systemd и не угадывает пути. Во время `daemon-reload` прежний процесс продолжает
работать, пока оператор не начнёт переключение.

Для управления службой нужны права на `systemctl show/is-active/stop/start`
именно `unbazarbot.service`. Если настроен ограниченный sudo, добавьте `--sudo`;
используется `sudo -n`. Скрипт не меняет sudoers, не получает пароль и не обходит
отказ. Если права не подготовлены, переключение запрещено.

## Проверить и подготовить новую версию

После однократной настройки в примере используются такие команды. На реальном
сервере агент подставляет подтверждённые пути, не запускает пример вслепую.

```bash
/opt/unbazarbot/current/.venv/bin/python /opt/unbazarbot/source/scripts/update_bot.py check \
  --repo /opt/unbazarbot/source
```

Команда получает `origin/main` в существующей проверенной рабочей копии и
показывает полный SHA, не меняя выпуск или службу. Проверку SHA и одобрение
изменений можно выполнить через GitHub Connector в ChatGPT; сам серверный
скрипт использует Git из локальной рабочей копии.

```bash
/opt/unbazarbot/current/.venv/bin/python /opt/unbazarbot/source/scripts/update_bot.py prepare \
  --repo /opt/unbazarbot/source --revision ПОЛНЫЙ_SHA_ИЗ_CHECK \
  --current /opt/unbazarbot/current --releases /opt/unbazarbot/releases \
  --config /etc/unbazarbot/config.yaml --env-file /etc/unbazarbot/bot.env \
  --database /var/lib/unbazarbot/bot.sqlite3 \
  --backups /var/lib/unbazarbot/backups
```

Новый выпуск строится из архива Git, получает собственную `.venv` и файл
`REVISION`, зависимости из `requirements.lock`. Скрипт проверяет компиляцию,
весь набор тестов и миграцию **копии** действующей SQLite. Сеть Telegram и
RouterAI для проверок не используется. Бот продолжает работать. Контрольные
суммы подготовленного кода сохраняются; изменённый выпуск не применяется.
Неудачная подготовка оставляет незавершённый каталог для диагностики; его нельзя
использовать как готовый выпуск или принудительно обходить проверку.

Если `main` изменился после выбора SHA, скрипт откажет: повторите `check`,
рассмотрите изменения и подготовьте новую точную ревизию. Новый код самого
скрипта сначала должен быть доступен в рабочей копии `source`; её обновляет
агент без изменения текущей службы. На первом запуске сначала сохраните все
ранее отслеживаемые рабочие файлы по `config_migration_ru.md`.

## Применить подготовленный выпуск

Повторите команду `prepare` со словом `apply`; при необходимости добавьте
`--sudo`. Параметры и SHA остаются теми же. Скрипт снова проверит подготовленный
выпуск и актуальную пробную миграцию, затем:

1. Сверит пути службы и внешних рабочих файлов.
2. Создаст закрытую копию конфигурации и секретов.
3. Остановит прежнюю службу и подтвердит отсутствие активного состояния.
4. Создаст окончательную согласованную копию SQLite с учётом WAL и проверит её.
5. Атомарно переключит `current`, запустит службу, проверит активное состояние без новых перезапусков в течение 10 секунд и проверит рабочую SQLite.

Рабочая база остаётся на прежнем внешнем пути. Два опросчика не запускаются.
Новая версия не удаляет накопленные обновления Telegram при старте; защита
расходов применяется и к сообщениям, накопленным за время переключения.

Успех скрипта означает работоспособность службы и локальных файлов. Он не
доказывает доставку Telegram или доступность RouterAI. Оператор дополнительно
проверяет `/about`, `/system`, `/access`, `/stats`, одно короткое безличное новое
голосовое и повтор из кеша. Обычное аудио и документы не должны создавать задания.
Запишите SHA и результат в обезличенный отчёт.

## Ошибка и восстановление

Если ошибка возникла до запуска нового процесса, возвращается прежняя ссылка
и запускается прежняя служба: новая версия ещё не могла принять сообщения.

После начала нового запуска правило строже: скрипт останавливает новую службу,
возвращает прежнюю ссылку, **оставляет службу остановленной и сохраняет текущую
базу**. Новая версия могла успеть изменить схему или обработать сообщение; старую
копию нельзя подставлять автоматически. Не воспринимайте возвращённую ссылку
как подтверждение работающего отката.

Оператор сохраняет копию нынешней базы, оценивает новые записи и совместимость
прежнего кода с её схемой. Сначала выполняет пробу прежнего кода на отдельной
копии. Если совместимость подтверждена, запускает прежнюю службу с нынешней
базой и проверяет её. Если требуется восстановление старой базы, отдельно
оценивает и переносит новые записи, только затем выполняет замену при остановленной
службе. Перед любой заменой снова сохраняются текущие данные. Файлы WAL/SHM не
копируют произвольной смесью со старой базой: используйте SQLite backup.

Последняя копия и сведения о прежнем выпуске находятся в каталоге, напечатанном
скриптом. Не удаляйте их до подтверждения работы. Чистка выпусков и копий не
автоматизирована: храните минимум три последних успешных обновления, текущую
копию и согласованную копию v5 до снятия потребности в откате. Перед удалением
отдельно проверьте, что каталог не является текущим или единственным источником
восстановления. Автоматическая проверка пробного восстановления входит в `prepare`.

## Служба, перезагрузка и журналы

`Restart=on-failure`, `KillMode=control-group` и достаточный `TimeoutStopSec`
позволяют остановить весь прежний экземпляр и корректно завершить его задачи.
Блокировка базы дополнительно запрещает второй новый процесс с тем же файлом.
Она не защищает разные серверы: старый v5 должен оставаться выключенным.

Проверка включённого автозапуска не заменяет испытание после перезагрузки.
Её проводят в согласованное окно, учитывая другие службы vserv; затем проверяют
единственный экземпляр и Telegram. Пока такого отчёта нет, #5 остаётся открытой.

Для ограниченного журнала службы можно отдельно настроить пространство journald
`unbazarbot`: `LogNamespace=unbazarbot` в службе и пример
`systemd/journald-unbazarbot.conf.example` как
`/etc/systemd/journald@unbazarbot.conf`. Сначала подтвердите поддержку на сервере.
Пример ограничивает журнал 64 МБ и 14 днями; диагностика:
`journalctl --namespace=unbazarbot -u unbazarbot.service`.
Старый журнал остаётся доступен обычной командой `journalctl -u unbazarbot.service`.
Настройка не выполняется скриптом обновления и не должна очищать журналы других служб.
